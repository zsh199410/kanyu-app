# Issue #73 P0 事实修正与替代方案（2026-11-13）

## 已确认与撤销

- 已确认：Surge 手机 `GET /v1/policy_groups/test_results` 仅返回策略组胜者（当前「免费节点池」胜者「香港2」），**没有逐节点延迟**。
- **撤销先前的 P0 可行性假设**。旧 `surge-report.js` 依赖不存在的逐节点字段，故当前不会采集有效数据；不要部署或宣称完成。
- 美国 VPS SSH 已通过密码登录修复；根因 `authorized_keys` 为空（0 行）；原公钥已补回、密钥登录已恢复，临时密码未保存。
- 统计校正：29 Trojan + 1 VMess + 17 SS = 47；`grep "ss,"` 误命中 `vmess,`。

## 发现的新官方路径

Surge iOS **6.0.0+** 支持：
1. 内部 `$httpAPI('GET','/v1/policies',{include_external:true},...)`，返回 `external-policies`，包含 `group`、`name`、`identifier`。
2. `$httpClient.head({url, policy: identifier, timeout:3}, cb)`，按指定外部节点发 HTTP HEAD，**无需新建策略组**。

官方文档：
- https://manual.nssurge.com/tools/http-api.html
- https://manual.nssurge.com/scripting/api.html
- https://manual.nssurge.com/scripting/cron.html
- https://manual.nssurge.com/policy-groups/url-test.html

这条路径**是手机主动测量**，违反 Issue 初稿“只允许胜者自动回传”若该约束按字面严格执行。须由机主认可“小批量无人值守后台主动探测”是可接受的动作后才可使用。**若仍禁止主动探测且接口只返回胜者，则不存在仅凭这些数据证明所有 47 节点均 <300ms 的方法**。

## 文件

- `probe-one.js`：只读枚举＋针对一个节点两次 HTTP HEAD 的手动 PoC；**不上传，不发布，不自动运行**。
- `probe-roundrobin.js`：实验性自动巡检，每小时最多四条，顺序轮换；持久化游标、失败样本、可重试的有限待上传队列。默认占位 token/URL 不发送到服务器，先准备数据。
- `pool.py`：在旧参考服务基础上新增 `/api/v1/probe` 和 `probe-status`，**只保存 HTTP 探测数据，不影响 `/api/v1/phone`、VERIFIED 判定和正式订阅发布**。
- `tests/test_pool.py`、`tests/test_probe.py`：Python 回归测试，17/17 本地通过。

## 检验顺序

1. **手机版本**：从 `$environment['surge-version']` 或 UI 确认 iOS Surge >=6.0.0。低版本只读接口不提供 `external-policies`，这条路径不成立。
2. **先手动运行 PoC**：在 Surge 中将 `probe-one.js` 声明为 `type=cron`，`timeout=15`，**先不要启用 cron 的自动运行**。如果必须设定计划，先禁用脚本并仅在编辑器内单次运行。最好关闭 Wi‑Fi、使用重庆移动蜂窝进行验证。
3. **所需日志**：输出 `version`、`count`、`state`、`warm_ms`、`second_request_ms`、`second_status`、`network_interface`。请将这几个字段脱敏贴入 Issue；不要公开 `identifier`、服务器 IP、订阅链接、密钥、Token。
4. **验证路由没有 DIRECT 回退**：在 Surge 请求记录中检查 HEAD 是否确实使用该代理；最好让自有 HTTPS 回显服务对比直接访问与代理访问的出口 IP。只看 204 不足以证明没有 DIRECT。
5. **验证两次 HEAD 能否复用底层连接**。两次脚本调用可能建立不同连接；`second_request_ms` 并不天然等于 Surge 原生 `url-test`，不能直接判为“手机 Surge 延迟<300ms”。需至少 10 个节点、每节点多次交叉校准，对照原生测速与 HTTP 探针的同一时间、同一测试 URL，统计误判率。
6. **网络类型准确性**：自动脚本只在 `$network.v4.primaryInterface` 匹配 `pdp_ipN` 且无 Wi-Fi SSID 时启动。若当前 Surge 版本接口返回其他值，会安全跳过，而不是错误标注蜂窝网络。
7. **后台可靠性**：Surge iOS cron `wake-system=false` 可能漏跑；初期只在真实运行/屏幕亮时验，监测 24–72h 实际执行次数。若后续开启 wake-system，评估电量和网络消耗。
8. **试运行期间生产现状不变**：原先 P1–P3 参考实现只读隔离测试，不替换 VPS 现有订阅。`/api/v1/probe` 采样数据**不会自动晋级 VERIFIED**，后续需校准、校验后另写有测试保护的升级逻辑。

## 运行 / 验证

`python3 -m unittest discover -s tests -v`、`node --check probe-one.js`、`node --check probe-roundrobin.js`。

原服务在测试目录创建数据库后运行（需要 Python 3.10+）：

```
SURGE_REPORT_TOKEN="<at least 32 random characters>" python3 pool.py --db ./trial.sqlite3 serve --host 127.0.0.1 --port 8765
python3 pool.py --db ./trial.sqlite3 probe-status
```

服务器只监听本机，经既有 Nginx/Caddy **HTTPS** 代理发布 `/api/v1/probe`。填写真实手机令牌前，确认反向代理 200 响应，并导入对应候选清单。不要提交真实代理账号、节点密码、公钥或 Token 到公开仓库。服务生产迁移须先备份。

## 注意

- 四条/小时只是能耗实验值，47 条完成一次需约 12 小时（前提是 cron 每小时实际执行且手机一直符合蜂窝条件）。并非保证 24 小时每条都有双次有效实测。
- `proxy policy` 发送的 HTTP 请求可能直接访问目标、可能受服务器端封锁影响，且当前缺少可证明的出口鉴别；**不据此发布认证的合格名单**。
- 在网络受限时 HTTP 204 可能返回其他状态/超时；不等于节点普遍不可用，需同 URL 的原生 Surge 对照样本。
