# 手机正式策略组 DIRECT 证据测试方案（GPT 6875033415 第 5 点）

> 本文件只是**方案**，不动手机配置、不改订阅、不动生产。是否跑、何时跑，
> 由机主定时间；跑之前须先由助手准备好 3 份测试订阅并核对。
> 目标：证明正式策略组在组员全失败 / 空组 / 单节点三种情形下**不落 DIRECT**，
> 或如实记录它落 DIRECT 的情形。

## 1. 为什么不能直接在正式组上测

- 正式组「免费节点池」是生产分流在用的组（YouTube / Google / Telegram 等
  规则指着它）。直接把它改成全失败/空组/单节点，会立刻影响正常上网。
- 因此用一个**临时测试组** + 一条**测试专用规则**做对照，正式组全程不动。
  测试组与正式组是同一个 `smart` 类型、同一个 url-test 配置（`interval=600,
  tolerance=100, timeout=0.3, test-url` 与正式组一致），只差成员内容——
  这样测到的是同类策略组的行为。

## 2. 准备（助手做，跑之前核对）

助手准备 3 份测试订阅（各 1 份，只含测试用节点，内容与正式池无关）：

| 订阅 | 内容 | 用途 |
|---|---|---|
| TEST-ALLFAIL | 3 条已知已死的节点（从已验证失败的节点里挑，指纹已记） | 全失败情形 |
| TEST-EMPTY | 0 行（空文件） | 空组情形 |
| TEST-SINGLE | 1 条当前原生通过的节点 | 单节点情形 |

每份订阅先在 VPS 上核对：行数、SHA256、每行可解析。测试组定义：

```
[Proxy Group]
DIRECT-TEST = smart, policy-path=<测试订阅地址>, update-interval=3600, interval=600, tolerance=100, timeout=0.3
```

测试专用规则（只影响一个测试域名，其余流量完全不动）：

```
[Rule]
DOMAIN,example.com,DIRECT-TEST
```

> 注意：`example.com` 只是占位。实际用哪个测试域名，由助手在跑之前定一个
> 平时不用的、能稳定返回出口 IP 的检测页（例如一个回显请求出口 IP 的
> HTTPS 页）。检测页的响应里只看“出口 IP 是代理出口还是手机运营商 IP”，
> **不要把原始 IP 发出来**，只记“与运营商 IP 相同 / 不同 / 请求失败”。

## 3. 三种情形的操作步骤（机主在手机上跑，每种约 2–3 分钟）

每种情形之前：关 Wi-Fi，只用移动数据；确认 Surge 在运行。

### 情形 A：全失败

1. 把 DIRECT-TEST 组的 policy-path 换成 TEST-ALLFAIL 订阅，刷新组，等成员数
   显示 3。
2. 对该组点一次测速，等全部测完：3 条应全部显示失败/超时。截图（成员+结果）。
3. 在手机浏览器打开测试域名（检测页）：
   - 记录 1：页面能不能打开？（能打开 / 打不开 / 超时）
   - 记录 2：若能打开，出口 IP 与运营商 IP 是否相同？
     （比对方法：先关 Surge 再开同一检测页，记下运营商直连时的出口 IP
     特征——只记“相同/不同”，不记 IP 本身。）
   - 记录 3：Surge → Dashboard → Requests 里找到这次请求，看它走了哪个
     policy（DIRECT-TEST / DIRECT / 失败）。截图。
4. **通过标准：请求打不开（失败），且 Requests 里没有走 DIRECT 的记录。**
   若请求能打开且出口 IP 是运营商 IP → 证明落 DIRECT，记为**不通过**，
   立即停测并报告（这是正式切换的阻断项）。

### 情形 B：空组

1. 把 DIRECT-TEST 组的 policy-path 换成 TEST-EMPTY 订阅，刷新组。
2. 记录 Surge 的表现（三选一，如实记）：
   - (a) 组显示 0 成员，仍可保留；(b) Surge 拒绝加载该组/报错；(c) 组直接消失。
   截图。
3. 再打开测试域名，记录同情形 A 的 3 项（能不能打开、出口 IP 相同与否、
   Requests 里的 policy）。
4. **通过标准：请求打不开，且 Requests 里没有走 DIRECT 的记录。**
   若 Surge 拒绝加载空组（b），本身就是 fail-closed 的证据，记下来即可，
   不必强行让它加载。

### 情形 C：单节点

1. 把 DIRECT-TEST 组的 policy-path 换成 TEST-SINGLE 订阅，刷新组，确认
   成员数 1，测速一次确认该节点成功且 <300ms。截图。
2. 打开测试域名：应能打开，且出口 IP 与运营商 IP **不同**（走了节点）。
   记录 Requests 里的 policy 应为 DIRECT-TEST。截图。
3. （可选，加做）在组里把这 1 条节点临时关掉/等它失败后，再打开测试域名：
   应打不开（同情形 A 的通过标准），不落 DIRECT。
4. **通过标准：单节点正常时走节点；节点失效时请求失败，不落 DIRECT。**

## 4. 收尾（必须做）

1. 删除 DIRECT-TEST 测试组与测试专用规则。
2. 删除 3 份测试订阅（助手侧删除托管文件）。
3. 核对正式组「免费节点池」成员数与测试前一致，正常上网一次确认无影响。
4. 把 3 种情形的截图 + 记录发给助手，助手整理成证据表回 #73。

即为正式切换的阻断项，须先拿出 fail-closed 方案（例如分流规则加
`no-resolve` / 指向明确的应急组并实测）再议切换。

## 6. 诚实边界

- 本方案测的是**同类 smart 测试组**的行为，不是正式组本身——因为正式组
  不能在生产流量上做破坏性测试。测试组与正式组的组类型、url-test 参数
  完全一致，结论可类推，但须在报告里写明这一点，不能说成“正式组已实测”。
- 空组情形下 Surge 若拒绝加载，属于 Surge 自身的 fail-closed 行为，是
  好消息，但它不等于“正式组空组时不落 DIRECT”的直接证据——正式组空组
  的情形只能在切换演练里用影子配置再验证。
- 本方案不涉及任何分流规则的改动；若测试证明会落 DIRECT，修复分流是
  另一个任务，须机主另外授权。
