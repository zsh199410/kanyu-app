# Issue73 — Pure-JS Ed25519 verification fallback (CODE-ONLY / NO-GO)

## Why and what this proves

Owner's actual iPhone Surge WebView/Generic script editor reported:
`secure=false, crypto=yes, subtle=no, digest=missing, trigger=editor`.
A signed credential-proof workflow cannot depend solely on
`crypto.subtle` in that observed runtime.

This proposal vendors independent, source-pinned JavaScript implementations
and a **pure read-only verification function**:
- **TweetNaCl.js** 1.0.3 `nacl-fast.js`, upstream blob
  `7ea5fb5883289b49f8d543f2d48af7132c3c6a6d`,
  public-domain license copied in `vendor/TWEETNACL-LICENSE.txt`.
  Its `nacl.sign.detached.verify` checks Ed25519 signatures in ordinary
  JavaScript, with its bundled SHA-512 implementation.
- **js-sha256** 1.0.0 `build/sha256.js`, upstream blob
  `edb15da8e79be6cb3878dc2b81c67d2cdbbb302e`,
  MIT license copied in `vendor/JS-SHA256-LICENSE.txt`.
  Its local `sha256` checks the actual candidate credential's fingerprint.
- `surge_purejs_signed_proof.review.js` enforces the exact signed proof
  domain, canonical JSON field order, old/new token ID exclusion, expected
  nonce, pinned key, issued/expiry windows, credential candidate hash,
  signature shape and Ed25519 verification.

The test executes the **actual vendored sources** in a VM containing
`isSecureContext=false` and **no** `crypto.subtle`, then checks a real
Ed25519 signature generated by independent Node crypto, a tampered
signature, different public key/candidate/nonce/token ID, expiry and other
fail-closed behaviors. These are CI synthetic fixtures, not real iPhone
or authenticated production service evidence.

## Production integration is NOT complete

1. This library is **not a standalone Surge script** and must never be
   registered as a generic/cron script or loaded via arbitrary CDN.
   The three code pieces require deterministic, audited bundling and
   a source SHA-pinned artifact. Neither this PR nor its CI installs it.
2. The actual iPhone runtime must prove it supports the vendored
   dependencies, `TextEncoder`, `Uint8Array`, `atob`, and that the
   verifier returns the expected result within the relevant Surge timeout.
   Do not assume the editor's non-secure origin behaves identically
   under a scheduled or intent trigger.
3. The verifier is **stateless**. A valid signed proof checked twice
   with the same trusted nonce will verify twice. This is explicitly
   demonstrated by a test and is a **KNOWN SECURITY LIMITATION**,
   not a replay-resistance PASS. Production needs a reliably durable
   one-time challenge/consume gate on device and server, including
   recovery after app kill/restart and rollback.
4. The production signer trust root must be pinned from an independently
   authenticated provisioning path. No public key supplied inside
   the signed response, downloaded JS or attacker-controlled data
   can authorize credential promotion. The proof candidate must come
   from a protected device slot, not a server-provided candidate.
5. Real signed HTTPS `/credential-proof` remains unimplemented on
   the user's production VPS with safe key custody/session auth.
   Real dual-token promotion, revocation, two cron cycles, backup
   token rollback, old-command reconciliation and anti-DIRECT checks
   remain required.

**Status:** `C3-C1=NO-GO`, `BOOTSTRAP_SECURITY_GATE=BLOCKED`,
`PR93_CUTOVER=BLOCKED`, `AUTO_DELETE=OFF`. No production changes;
old `1795063030` command stays `OUTCOME_UNKNOWN`; 21 pinned nodes
