# 手机 DIRECT 三场景测试 · 一页操作指引（Issue #73，D4 方案压缩版）

> 只写操作与记录，不写原理。正式组全程不动；手机实测本身未做，须机主在手机上跑。

## 前置

1. 正式组「免费节点池」不动；新建临时测试组 `DIRECT-TEST`（与正式组同 `smart` 类型、同 url-test 参数：`interval=600, tolerance=100, timeout=0.3`）。
2. 加一条只影响测试域名的测试规则（其余流量不动）；助手提前备好三份测试订阅并核对行数与 SHA：全失败 3 条已死节点 / 空组 0 行 / 单节点 1 条新鲜原生通过（<300ms，24 小时内，当前 served 版本 SHA 下）。
3. 助手先记 served 版本锚点：served 文件 SHA 与行数（门禁版 / 旧版注明）。跑之前关 Wi-Fi，只用移动数据，确认 Surge 在运行。

## 情形 A：全失败组

1. `DIRECT-TEST` 的 policy-path 换成全失败订阅，刷新，等成员数显示 3。
2. 对该组点一次测速，等测完：3 条应全部失败 / 超时。截图（成员 + 结果）。
3. 手机浏览器打开测试域名，记三项：① 能不能打开（能 / 打不开 / 超时）；② 若能打开，出口 IP 与运营商 IP 是否相同（只记相同 / 不同，不记 IP 本身；运营商 IP 特征先关 Surge 打开同一页比对一次）；③ Surge → Dashboard → Requests 里这次请求走了哪个 policy。截图。
4. **通过标准：请求打不开，且 Requests 里没有走 DIRECT 的记录。** 若能打开且出口 IP 是运营商 IP，即落 DIRECT，记不通过，立即停测并报告。

## 情形 B：空组

1. `DIRECT-TEST` 的 policy-path 换成空组订阅，刷新。
2. 记 Surge 的表现（三选一，如实记）：(a) 组显示 0 成员仍可保留；(b) Surge 拒绝加载该组 / 报错；(c) 组直接消失。截图。
3. 再打开测试域名，记同情形 A 的三项（能不能打开、出口 IP 相同与否、Requests 里的 policy）。
4. **通过标准：请求打不开，且 Requests 里没有走 DIRECT 的记录。** 若为 (b)，本身就是 fail-closed 的证据，记下来即可，不必强行让它加载。

## 情形 C：单节点组

1. `DIRECT-TEST` 的 policy-path 换成单节点订阅，刷新，确认成员数 1，测速一次确认该节点成功且 <300ms。截图。
2. 打开测试域名：应能打开，出口 IP 与运营商 IP**不同**（走了节点），Requests 里的 policy 应为 `DIRECT-TEST`。截图。
3. （可选，加做）把这 1 条节点临时关掉 / 等它失败后，再打开测试域名：应打不开，不落 DIRECT。
4. **通过标准：单节点正常时走节点；节点失效时请求失败，不落 DIRECT。**

## 收尾

1. 删除 `DIRECT-TEST` 测试组与测试专用规则。
2. 删除三份测试订阅（助手侧删除托管文件）。
3. 核对正式组「免费节点池」成员数与测试前一致，正常上网一次确认无影响。
4. 把三情形的截图 + 记录发给助手整理成证据表回 #73。
5. 助手重取 served 文件 SHA 与行数，与测试前锚点逐项核对，必须完全一致；若变了，先停下来查原因，不要继续验收。

**判定：三种情形全部不落 DIRECT 才算证明完成；任一落 DIRECT 即正式切换阻断项。**
